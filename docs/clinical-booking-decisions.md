# Clinical booking and appointment decisions

Customer service cards and primary/additional booking dropdowns show service names without prices. Stored pricelist images remain managed separately by administrators.

Consultation, Vaccination and Laboratory Testing offer radio lists from the supplied clinic reference. Customers choose one specific option for each selected category. Consultation has 17 options; laboratory has CBC Plain, CBC Basic Chemistry and Comprehensive Chem, with included tests shown as descriptive text. Vaccines follow the reference species labels: cats get 4 in 1, dogs get 5/6/8 in 1 and Kennel Cough, and both get Anti Rabies and Doctor's Fee. Switching pets clears specific service selections. The API validates against the saved pet's species, rejects duplicate selections for a category, and persists canonical option IDs/names in clinicalSelections. Legacy appointments can still be approved without reselecting services.

Appointment status Expired is presented as No Show throughout customer/admin/staff appointment screens. Legacy Expired and No-show values are normalized on load. New elapsed-pending records use No Show; existing approved-appointment behavior remains unchanged.

Staff/admin rejection uses the reason form. Cancellation uses a simple confirmation prompt with no reason fields. The category dropdown includes only A. Staffing and Clinic Capacity, B. Pet Health and Medical Suitability, and C. Other. A has exactly the three approved reasons; B has exactly the two approved reasons. Options under A/B use exclusive radios. Selecting a category disables the other category options; Change category clears the choice. C uses a required textarea, validated on client and server, trimmed before persistence, with 10–1000 character limits and a letter/number requirement.

The server stores decision (category, reason, by, at), plus rejectionReason, on the appointment. It writes a customer notification containing the specific rejection reason in the same transaction. Staff cancellations save without a reason and keep a generic cancellation notification. The existing notification subscription delivers it to the customer account. Customer cancellations retain their existing workflow and cannot forge staff reasons. Legacy rejected/cancelled records are readable. The customer appointment detail shows the stored explanation. User text is rendered through React as text.

Verification uses shared-model tests, a mocked Firestore transaction controller test for canonical clinical selections and atomic decision/notification persistence, appointment normalization/rendering tests, and browser fixtures for radio lists and decision forms. Browser fixtures do not create live customer appointments or send real notifications.
