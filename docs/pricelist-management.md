# Pricelist management
Administrators open Manage Services and Pricelist from the dashboard or portal sidebar. Each category has an independent image. Selection validates MIME type, size (5 MB, configured in shared/pricelists.mjs and server/src/utils/pricelistImage.js), and browser image decoding. Selecting a file only creates a local preview.

Save Changes opens Confirm Changes. Cancel retains the preview. Confirm and Save sends the image to the existing authenticated Express API, which independently requires the stored admin role and validates size, encoding and binary image signatures. Uploaded raster images are served as image content, never executed.

Firebase Admin writes a unique object under pricelists/{category}/{uuid} in the existing Firebase Storage bucket, then transactionally publishes its reference in servicePricelists/{category}. Revision conflicts reject stale edits. A failed database publication deletes the pending object where possible; the previous reference remains intact. Successful replacement attempts to remove the old object. Cleanup failure can leave an unreferenced object. Success is shown only after the API completes. Authenticated GET /api/auth/pricelists loads customer and admin displays through the Admin SDK, avoiding browser Firestore rule dependencies. Clients refresh every 30 seconds, on window focus, and after successful saves. The admin also applies the saved API response immediately.

Pricelist reads and writes now use the backend; no Firestore rules deployment is needed for this module's API workflow. Direct client writes to servicePricelists are denied. Storage rules remain deny-all: only the existing Admin SDK uploads; saved images are available through download-token URLs. No new dependencies, paid services, or authentication design changes were introduced. Ensure the existing FIREBASE_STORAGE_BUCKET (or configured storage bucket alias in server configuration) points to an accessible provisioned bucket and the backend service account can write objects. No manual migration is required: the first authenticated load transactionally creates only missing records for the five categories with empty image references and revision zero. Existing records remain unchanged. Empty records display unavailable placeholders, not uploaded status. Load errors include backend messages and a Retry loading action.
