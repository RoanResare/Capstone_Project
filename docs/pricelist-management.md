# Pricelist management

Administrators open Manage Services and Pricelist from the dashboard or portal sidebar. The replacement picker supports clicking, keyboard selection, and dropping one JPG, PNG, or WebP image up to 5 MiB. Selection only creates a pending image; it does not publish anything.

Images are now stored directly in Firestore as Base64 data URLs in servicePricelists/{category}.imageUrl. Firebase Storage is no longer used for pricelist saves, so no Storage bucket or Blaze billing account is needed for this feature. Existing URL-based records continue displaying until replaced. The authenticated API and stored admin-role authorization are unchanged. Direct client writes remain denied by the existing Firestore rules.

Client optimization preserves the original image when its data URL already fits. Larger images are drawn to canvas, trying lossless PNG and WebP/JPEG at quality 0.95, 0.88, and 0.82 before progressively reducing resolution. The initial longest edge is capped at 4096 pixels; the algorithm does not shrink below a 1600-pixel longest edge (or the original resolution for smaller images). Browser canvas performs image decoding and encoding; no new dependency or paid service is required. Images above 40 million pixels are rejected to bound canvas memory usage.

The maximum complete data URL is 900 KiB (921,600 bytes), including Base64 expansion and MIME prefix, leaving over 100 KiB below Firestore's 1 MiB document limit for the fixed metadata. Both browser and server enforce this bound. The server also validates canonical Base64, image MIME type and binary signatures before any write. The original file-selection limit remains 5 MiB. An image that cannot fit at the quality/resolution floor is rejected with guidance to crop borders or export a simpler pricelist instead of silently degrading it further. Readability depends on the source: admins see the exact optimized result and should inspect prices in the preview before confirming.

Save Changes opens Confirm Changes. Confirm and Save sends the prepared data URL and expected revision. A Firestore transaction checks the revision and replaces the record with imageUrl, an empty legacy objectPath, the incremented revision, timestamp, and admin UID. There are no object uploads or storage cleanup steps. A conflict or failed commit preserves the previous record. Success appears only after the transaction completes, and the saved response updates the admin display immediately. Customers use the same imageUrl field, which supports both legacy URLs and new data URLs. Existing refresh behavior remains: every 30 seconds, on window focus, and after successful saves.

First authenticated loading initializes only missing records for the five categories with revision zero. Existing records are preserved. No data migration or Firestore rules deployment is required. Firebase Storage configuration elsewhere in the project is unaffected.

Validation: 13 focused tests passed, including 5 MiB input handling, encoding preference, adaptive resizing, quality-floor rejection, oversized server payload rejection, transaction conflicts, persistence, and database failure behavior. Browser APIs in compression tests are simulated; actual browser rendering and visual text readability were not tested automatically. The production Vite build passed. A live controller save and read-back against Firestore passed using an isolated temporary document, which was deleted afterward; existing category documents were not altered.

Firestore limits reference: https://firebase.google.com/docs/firestore/quotas
