# Session Connection Security

Registration availability, login, and OTP completion check the current server-observed IP with ipapi.is. Protected requests and the authenticated-session background monitor use the same regional policy. Network blocking requires both a recognized country outside the whitelist and VPN/proxy/Tor/hosting evidence or a configured network range. Only that confirmed non-regional detection persists revocation in `sessionSecurity/{uid}`, revokes Firebase refresh tokens, and rejects the request before its action executes. Existing Firestore rules enforce persisted revocation as well.

Session monitoring is silent: no loading gate or flashing verification screen. A two-second poll checks `/auth/session-security` while signed in, including dashboards, `/portal` modules, and public pages; authentication forms skip polling. Navigation, router navigation/revalidation state changes, focus, page restoration, connectivity restoration, visibility restoration, and supported network-change events also trigger checks. Pointer, keyboard, and form-change interactions trigger checks at most once per second. Overlapping checks are coalesced, with a fresh check queued when events arrive during a request. Hidden tabs resume checking when visible. Sensitive Firestore save/profile/password workflows have server preflights. Confirmed non-regional violations trigger logout, clear remembered/trusted-device metadata, preserve a security warning, and redirect to `/login`. Transient network errors retry without logout. The 30-minute inactivity timeout and Remember me expiration remain unchanged.

## Provider Configuration

With no override, the backend uses `https://api.ipapi.is/?q={ip}&key={api_key}` with `FRAUD_GEO_LOOKUP_API_KEY`. It reads `location.country_code`, `location.country`, and `location.state`/`region`, with top-level country and region aliases for minimal responses. Country code and region are saved on session bindings and updated after subsequent successful checks, including location changes for the same IP. Positive `is_vpn`, `is_proxy`, `is_tor`, `is_hosting`, and `is_datacenter` flags (or supported nested aliases) provide network evidence only outside the whitelist. The keyed ipapi.is response uses `is_datacenter` for hosting detection, as described in its [documentation](https://ipapi.is/developers.html). A `hosting` classification in `company.type` or `asn.type`, or `private_relay`/`secure_web_gateway` egress metadata, also provides evidence. Known VPN/hosting company and ASN names provide a fallback: Proton, Windscribe, PrivadoVPN, TunnelBear, Hetzner, Leaseweb, DigitalOcean, Vultr, OVHcloud/OVH SAS, Amazon Data Services/AWS, and Microsoft Azure. Matching is case-insensitive with word boundaries; generic words such as `cloud`, `network`, and `privacy` do not block.

The absolute network whitelist covers Philippines (`PH`), Singapore (`SG`), Hong Kong (`HK`), Brunei (`BN`), Cambodia (`KH`), Indonesia (`ID`), Laos (`LA`), Malaysia (`MY`), Myanmar (`MM`), Thailand (`TH`), Timor-Leste (`TL`), and Vietnam (`VN`). These locations override all network flags, provider-name heuristics, and configured blocked ranges. Names and codes are case-insensitive; any whitelist evidence wins if country fields conflict. Unrecognized or missing country information fails open even when network evidence exists. Region names are metadata, never a blocking signal. Country shifts and clean IP changes never trigger blocking on their own. This whitelist concerns network restrictions; normal authentication, account status, and previously revoked credentials remain enforced.

`SESSION_BLOCKED_NETWORK_CIDRS` optionally lists comma-separated verified VPN/proxy/hosting IPv4 or IPv6 addresses/CIDRs. Matching uses Node's `net.BlockList` only after a successful geolocation lookup confirms a non-whitelisted country. These ranges cannot block whitelisted locations or connections during provider outages. Invalid entries fail configuration loading. No speculative ranges are preloaded. Checks use the current IP without caching a previous blocked decision. Logs include concise block/error reasons only, never provider URLs or API keys.

An anonymous ipapi.is response contains a `docs` link to its free-tier explanation and omits threat fields. The service warns once per process when it sees this format. Ensure `FRAUD_GEO_LOOKUP_API_KEY` is configured in the deployed backend environment; local `.env` values are not automatically transferred to Render. Anonymous responses provide weaker name-based fallback detection, not a verified clean connection. No IP-intelligence policy can guarantee detection of every VPN app or zero classification errors; browser code cannot directly inspect installed VPN apps.

Optional `FRAUD_GEO_LOOKUP_URL` and `FRAUD_GEO_LOOKUP_API_KEY` overrides remain supported. Providers may return explicit `security.vpn`, `security.proxy`, or `security.tor` values. Boolean values and their `true`/`false` or `1`/`0` representations are supported.

For IPWhois with a plan that includes threat detection:

```dotenv
FRAUD_GEO_LOOKUP_URL=https://ipwhois.pro/{ip}?key={api_key}&security=1
FRAUD_GEO_LOOKUP_API_KEY=your-provider-key
```

The API key stays on the server. HTTP errors (including quota exhaustion), provider error payloads, invalid JSON, connection failures, and five-second timeouts always allow access without network revocation. Missing or unrecognized geography also allows access. Configured ranges never override this fail-open policy. `FRAUD_FAIL_CLOSED` does not affect IP checks; it only controls other fraud/email-provider policies.

Express traverses trusted loopback, link-local, and private ingress hops, stopping at the nearest untrusted address rather than assuming a single proxy hop. Set `TRUSTED_PROXY_CIDRS` to comma-separated IPs/CIDRs only if the deployment has additional known public ingress proxies. The deployment must prevent direct access around its ingress, which must sanitize forwarded headers. Never set arbitrary client IP headers or trust all public proxies. See [Express proxy guidance](https://expressjs.com/en/guide/behind-proxies/). Client country headers are not used as evidence. Private, invalid, or missing IPs skip the provider lookup rather than blocking access.

## Email Validation

Known disposable domains, including `hudzer.com`, `yzcalo.com`, Mailinator, Temp Mail, 10 Minute Mail, Throwaway Mail, and Guerrilla Mail, return `Temporary or disposable email addresses are not allowed` with HTTP 400 and code `DISPOSABLE_EMAIL_DOMAIN`. Registration checks email syntax and this built-in list on every attempt, before checking duplicates or creating an identity. Reused names, passwords, contact numbers, or registration IPs never exempt an email. Matching ignores case and includes subdomains without rejecting unrelated domains containing similar text.

Registration accepts syntactically valid major-provider, business, institutional, educational (including `sti.edu`), and non-`.com` domains unless specifically listed as disposable. It does not use DNS failures or external disposable/deliverability heuristics to block registration. Both frontend Firebase signup helpers call the backend registration check before creating an account, even when invoked directly; backend admin/staff account creation runs the same local validation. Rejection before identity creation preserves any current session and stored tokens. The existing verification-code flow is unchanged. Mailbox ownership must be established through verification, not inferred from domain checks. The built-in list is a curated snapshot and must be extended as disposable services add new domains.

Other email-deliverability workflows (profile updates and password recovery) retain their MX/provider validation. Malformed addresses still return `Illegitimate email cannot be verified`. These application checks do not disable the Firebase project's public signup API; enforcing the same policy against callers who bypass the application entirely requires a Firebase Authentication blocking function or server-only account creation with client signup disabled in the project configuration.

Session IP bindings are stored in server-managed `sessionConnections` records; signed `connectionIp` claims protect the interval before the first poll. Sessions without that claim bind to the first successfully checked connection. Configure Firestore TTL on `sessionConnections.expiresAt` to clean up expired records. Persisted revocations still require a fresh login.

## Clean-Network Recovery

Login/OTP checks evaluate the current public server-observed IP using the regional whitelist first. A confirmed non-regional network block displays `Blocked VPN IP address`. During an active session, an allowed IP change updates the persisted session baseline. Whitelisted locations and provider failures never trigger a new network revocation. A confirmed blocked IP terminates the session and stores a one-time warning shown on the login page. Browser responses carry a session epoch, so delayed responses from a logged-out session cannot terminate a fresh session for the same UID.

New tokens are issued only after an outstanding revocation finishes and its seconds-based cutoff has passed (normally less than one additional second). Old revocation metadata is preserved to reject token replay, but fresh sessions get new IP bindings. A transaction starts revocation only once for an old token: concurrent or late requests cannot advance its cutoff or revoke refresh tokens again. Clean requests also recheck token revocation after the provider lookup. No account-level VPN penalty is applied; after returning to a normal network, authenticate again normally. Refreshing an already terminated session still requires a fresh login; revoked credentials are never restored.

Logout clears transient auth tokens from both local and session storage and invalidates pending profile hydration immediately. A verified fresh login signs out any leftover Firebase identity before installing and force-refreshing the new custom-token session, consumes old warning markers, and protects that handoff from stale auth-state callbacks. Application/customer data and legitimate Remember me settings are not globally wiped. A pending server revocation older than 30 seconds is repaired by repeating Firebase revocation during a verified login, preserving the old-token cutoff rather than removing security records.

Deploy both backend and frontend changes. Tests cover silent rendering, polling/navigation/network events for every role, clean IP re-baselining, VPN/proxy/Tor/hosting detections, token replay, and transient lookup failures. Browsers cannot directly inspect a phone's VPN app. Detection occurs on the next request or poll, not instantaneously when a VPN icon appears. IP intelligence identifies known VPN/proxy/hosting endpoints, not every private VPN.
